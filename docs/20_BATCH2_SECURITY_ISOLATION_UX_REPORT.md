## 2. عزل قاعدة الاختبار لكل جلسة (P3-8 + الحادثة السابقة)

### 2.1 التصميم

- **القيد الحاسم:** `apps/api/test/http-e2e/env.ts` يرفض أي اسم قاعدة لا يطابق `^khabir[_-]test$` بالضبط؛ لذلك لا يمكن تسمية قاعدة الجلسة `khabir_test_batch2`. العزل يُنفَّذ على مستوى **الخادم** لا الاسم:
  - compose project فريد: `khabir-test-session-<id>`،
  - حاوية فريدة: `khabir-test-session-<id>-db`،
  - منفذ مضيف مخصص (افتراضي `5434`)،
  - قاعدة داخل الحاوية: `khabir_test` (كما يشترط الحاجز).
- الجلسة المنفّذة: `KHABIR_TEST_SESSION_ID=batch2` / منفذ `5434` → حاوية `khabir-test-session-batch2-db`.
- الحواجز في السكربتات: رفض معرّف جلسة غير صالح، رفض المنافذ `5432` و`5433` (تطوير/مشتركة)، رفض إعادة استخدام حاوية يملكها مشروع compose آخر، وقيام `teardown` بإزالة **المشروع الموسوم فقط**.
- `env.ts` **لم يُعدَّل**؛ الحماية الأصلية (fail-closed) باقية بالكامل.

### 2.2 الأدلة

- `provision-session-db.mjs` طُبِّق بنجاح: **19 migration** على قاعدة الجلسة + كتابة/قراءة marker `khabir-test`.
- مسار HTTP الحقيقي عمل على قاعدة الجلسة: **5 ملفات / 34 اختباراً أخضر** (القسم 4) — أي أن حاجز `env.ts` قبل عنوان الجلسة ومرّرت الهوية.
- `teardown-session-db.mjs` أزال الحاوية والشبكة والـ volume؛ `docker ps -a` بعدها لا يُظهر أي أثر للجلسة، والمنفذ `5434` مغلق.
- القاعدة المشتركة `khabir-v21-test-db` (5433، healthy) **لم تُلمس** طوال الدفعة.

### 2.3 ملاحظة تشغيلية (شفافية)

أول تشغيل للسكربت فشل في خطوة انتظار الجاهزية برسالة Prisma عابرة («the URL must start with the protocol prisma://») دون أي تغيير في الشيفرة؛ أعاد التشغيل الثاني نفس الخطوات فنجح كاملاً (إنشاء + 19 migration + marker). القاعدة كانت جديدة تماماً، ولم يحدث أي اتصال/كتابة على قاعدة أخرى. أُبقيت الظاهرة موثّقة ولم تُخفَ.

## 3. إغلاق فجوة حذف المراجعات (الخادم سلطة)

الاختبار الجديد `admin-review-removal.http.spec.ts` يعمل عبر HTTP الحقيقي (guards → validation → service → Prisma) على قاعدة الجلسة:

| # | الحالة | النتيجة المتوقعة | مؤكَّدة |
| --- | --- | --- | --- |
| 1 | بلا توكن | 401 + بقاء المراجعة + صفر audit | ✓ |

## 5. إصلاحات الواجهة والتحقق البصري/الوصولي

### 5.1 المنفَّذ

- **P3-5 (خطأ حقيقي):** `requestEnvelope` كان يُجري `JSON.parse` خارج `try`؛ استجابة غير JSON (بوابة/5xx HTML/جسم مبتور) كانت تُظهر `SyntaxError` غير معالج. الآن تُرفع `AdminApiError(res.ok ? 502 : res.status, 'INVALID_RESPONSE', 'تعذر قراءة استجابة الخادم. حاول مجددًا')` مع مسح الجلسة عند 401.
- **P3-3:** `type` لم يعد نصاً حراً: قيمة ثابتة `general` (إشعار تشغيلي إلزامي لا يخضع لتفضيلات الكتم) في حقل للقراءة فقط + شرح + 3 قوالب سريعة تعبّئ العنوان/المحتوى (قابلة للتعديل). هذا يمنع إساءة استخدام أنواع `request_status`/`subscription` القابلة للكتم أو الخلط بينها.
- **P3-7:** عند تجاوز 100 فني: نص «تُعرض أول 100 من N…»، حقل بحث (يظهر عند ≥10 خيارات) يصفّي بالاسم/المعرّف، وإدخال معرّف يدوي كمسار بديل، مع تذكير أن الخادم يتحقق من توثيق الفني. زر التأكيد يُفعَّل بأي من الاختيار أو المعرّف اليدوي.
- **P3-2:** تحقّق أن الوصف لم يعد مطابقاً: لا توجد بطاقات placeholders ولا «0.00 ر.س» في نسخة HEAD ولا في الشجرة الحالية؛ تبويب المنح نموذج إدخال فقط. لا تغيير لزم — وُثّق كبند متقادم.
- **P3-1/P3-4:** إصلاحات Batch 1 قائمة (`formatDateAr`، توكنز النجاح/الخطأ). فحص axe الجديد على البناء الحالي: **0 مخالفات** (القسم 5.3).

### 5.2 التحقق الحي (Playwright على بناء نهائي)

بيئة معزولة: API على `:3012` موجّه لقاعدة الجلسة، لوحة مبنية بـ `NEXT_PUBLIC_API_URL=http://localhost:3012` وتعمل على `:3001`، وحساب `admin@qa.local` (super) من `seed-qa.mjs` بعد إضافة 101 فني موثّق وطلب معلّق لأغراض العرض.

- **إشعار فعلي:** تعبئة قالب → «إرسال» → dialog «تأكيد الإجراء» → تأكيد → تحقق DB: `notification.type = "general"` و`titleAr = "متابعة طلبك"` والتدقيق `admin.notification.create` مسجّل — أي أن القيمة المغلقة هي ما يُرسل فعلاً.
- **التعيين:** فتح «تعيين فني» يُظهر «تُعرض أول 100 من 102 فني موثق…»، البحث «فني تجريبي 10» يصفّي إلى خيار واحد صحيح.
- الفحص البصري: RTL سليم، لا letter-spacing على العربية، لا كسر تخطيط في الحالتين.

## 6. تصحيح ادّعاء في تقرير الدفعة 1

`docs/19` وصف اختبارات `admin-payments-decisions.e2e.spec.ts` بأنها «خادم NestJS مرفوع فعلاً + Prisma». **دقيق جزئياً:** الخادم HTTP حقيقي ويُقلع `dist/app.module` عبر supertest، لكن **Prisma ليس حقيقياً** — يُستبدل `PrismaService` بـ `createFakePrisma` من `apps/api/test/fake-prisma` (in-memory). لذلك:

- تلك الاختبارات تحقّق التوجيه/الحراس/التحقق/المنطق فوق fake store، لا سلوك Postgres الحقيقي (قيود، معاملات، تزامن).
- التغطية الحقيقية على قاعدة فعلية هي مسار `test/http-e2e/` فقط، وهو ما وسّعته هذه الدفعة.
- تصحيح التقرير السابق مذكور هنا؛ لم يُعدَّل `docs/19` (حماية سجل التسليم) — هذا التصريح هو المرجع.
